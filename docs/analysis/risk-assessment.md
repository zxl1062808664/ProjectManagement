# 风险评估

## 风险总览

| 风险 | 级别 | 说明 | 缓解策略 |
| --- | --- | --- | --- |
| 单体前端脚本继续膨胀 | 高 | 当前 `app.js` 已同时负责状态、渲染和存储 | 先拆前后端边界，再拆前端模块 |
| 本地数据与云端数据切换 | 高 | 游客模式与登录后云端模式可能产生数据冲突 | 明确“首次登录导入/合并”流程，并记录来源 |
| SQLite 关系建模错误 | 高 | 项目、任务、标签、子任务、会话涉及多表关联 | 先固化 schema 和约束，再写 API |
| 密码与会话安全不足 | 高 | 不可直接明文存储或弱 session 管理 | 使用密码哈希、随机 token、服务端会话校验 |
| 导入 JSON 不受控 | 中 | 错误或恶意数据可能污染数据库 | 服务端做结构校验、长度限制和归属校验 |
| 无测试基线 | 中 | 当前没有自动化测试，回归风险高 | 为 API 和关键流程补基础测试 |
| 目录重组引入回归 | 中 | 从根目录静态文件迁移到前后端结构时容易破链接 | 分阶段迁移，先保证静态页面继续可访问 |
| 无部署与运维文档 | 中 | 完成代码后无法稳定复现启动 | 补运行说明、环境变量和数据文件说明 |

## 关键技术风险

## 1. 认证体系选择

本项目默认方案是“账号密码 + 本地会话”。这意味着后端至少要负责：

- 密码哈希
- 登录态生成
- 请求身份校验
- 过期与登出处理

如果为了图快把会话状态仅保存在浏览器，将无法真正实现安全的多用户隔离。因此认证必须以后端为真相来源。

## 2. 同步语义定义不清

“云端同步”最容易做坏的点不是 API，而是语义。如果不先明确行为，最终很容易出现不可预测结果。

推荐策略：

- 未登录：数据保存在浏览器本地
- 登录后：主工作区切换到云端
- 若本地存在游客数据：提供一次性“导入到当前账号”入口
- 导入默认采用“追加导入新项目/任务”而不是双向自动 merge

这比隐式自动合并更稳。

## 3. 前端状态失控

如果继续沿用单文件渲染模式，后续至少会新增：

- 当前用户
- 当前项目
- 项目列表
- 标签集合
- 子任务集合
- 同步状态
- 会话过期状态
- 导入导出状态

这些状态不适合继续塞进一个文件里直接操作 DOM。必须建立清晰的状态层和 API 层。

## 4. 数据完整性

需要重点防止以下问题：

- 删除项目后留下孤儿任务
- 删除任务后留下孤儿子任务和标签关联
- 越权访问其他用户项目
- 导入 JSON 时创建重复或无归属数据

对应方案：

- 使用外键和删除级联
- 所有查询以当前用户为根进行过滤
- 写操作统一走 service 层

## 5. 视觉改造与功能改造相互干扰

当前 UI 已经有明确视觉语言，风险不在“重做样式”，而在功能大改时破坏现有布局稳定性。应遵循：

- 先完成数据和交互骨架
- 再把登录、多项目、标签、子任务逐步挂入现有布局
- 尽量复用当前的视觉变量和卡片风格

## 实施建议

开发顺序建议固定为：

1. 项目结构和服务端骨架
2. 数据库 schema 和认证
3. 项目/任务/标签/子任务 API
4. 前端改造与 API 接入
5. 游客模式与云端模式桥接
6. 导入导出、测试和文档

这个顺序的核心原因是：只有先稳定好“身份 + 数据模型 + API”，前端功能扩展才不会返工。
